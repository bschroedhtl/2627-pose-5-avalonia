1  Avalonia Basics

Avalonia is a cross-platform UI framework for .NET. You describe the user interface in XAML, an XML-based markup language, and write the logic in C#. The same app runs on Windows, macOS and Linux, and Avalonia can also target the browser and mobile devices.

This chapter covers the foundations: how an Avalonia project is put together, how XAML works, and how a window reacts to clicks. Along the way you build your first app, HelloAvalonia, in four labs. Each lab starts from where the previous one stopped, so work through them in order.

1.1 Why Avalonia?

1.1.1 The landscape in 2026

There is no reliable market-share figure for desktop UI frameworks. Most desktop applications are internal tools that never show up in any statistic. The signals that do exist all point the same way:

  • Web frameworks such as React, Angular and Node.js are used by far more developers than any native desktop toolkit. Many “desktop” apps are web technology too: VS Code, Slack, Teams and Discord are built with Electron.
  • WPF, Microsoft’s Windows-only desktop framework, has the largest installed base in the .NET world. It is in maintenance mode, but countless enterprise, industrial, medical and finance applications run on it and still have to be maintained and extended.
  • Avalonia is the fastest-growing .NET desktop framework and the leading cross-platform one. Avalonia 12 was released in April 2026; JetBrains, Unity, Autodesk and NASA are among its users.

As a rough order: web and Electron apps are far ahead, then WPF and WinForms (both legacy), then Avalonia (growing), about level with MAUI and Qt.

1.1.2 Why learn it after three years of web development?

  • A different programming model. A desktop app is one long-running process that keeps its state, has a UI thread and binds the UI to data. A web app mostly answers stateless requests and re-renders a DOM. Desktop development makes you think about state and threading in ways web development rarely does.
  • WPF comes almost for free. Avalonia’s XAML, bindings, styles and the MVVM pattern map almost one to one onto WPF. Maintaining existing WPF code is where many junior .NET jobs are: machine control panels, test benches, in-house tools.
  • It runs everywhere, including on your own laptop, whatever operating system it has.
  • Some software doesn’t belong in a browser: anything that talks to hardware (serial ports, USB, fieldbuses), runs offline or in isolated networks, computes heavily on the local machine, or drives an embedded Linux touch panel.
  • Same stack as the backend. It is the same C#, the same tooling, the same dependency injection and the same unit tests you already know from ASP.NET Core.
  • The patterns transfer. Observable state, commands and composing a UI from components are close relatives of what React and Angular do.

To be honest about it: most of you will build more web frontends than desktop UIs. Avalonia widens your skill set; it doesn’t replace your web skills.

1.2 Setting up

You need:

  • the .NET 10 SDK,

  • an IDE: JetBrains Rider with the AvaloniaRider plugin, or Visual Studio Code with the Avalonia for VS Code extension,

  • the Avalonia project templates. Install them once per machine:

    dotnet new install Avalonia.Templates
TipLab 1.1: Create and run the project

🎯 Goal. An empty Avalonia app that starts and shows a window.

  1. Create the project and a solution file for it:

    dotnet new avalonia.app -n HelloAvalonia -o HelloAvalonia
cd HelloAvalonia
dotnet new sln -n HelloAvalonia
dotnet sln add HelloAvalonia.csproj

    The solution file (HelloAvalonia.slnx) is optional for a single project, but it lets Rider open the folder as a solution.

  2. Open HelloAvalonia.csproj and add one line to the first <PropertyGroup>:

    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>

    From now on every compiler warning stops the build. Warnings are almost always real problems (a possible null, an unused variable), and this way you can’t ignore them.

  3. Start the app:

    dotnet run

✅ Check. A window titled HelloAvalonia opens and shows the text Welcome to Avalonia!. Close it before you continue.

1.3 The project files

An Avalonia application strictly separates what the UI looks like from what it does. The layout lives in a XAML file with the extension .axaml; the logic lives in a C# file of the same name with .axaml.cs appended, the code-behind. Your new project contains:

File Purpose
Program.cs The Main entry point. Configures and starts the Avalonia application.
App.axaml / App.axaml.cs The application object: the global theme, and which window opens at startup.
MainWindow.axaml The view: the layout and controls of the main window, in XAML.
MainWindow.axaml.cs The code-behind: the C# logic that belongs to MainWindow.axaml.
HelloAvalonia.csproj The project file: target framework and NuGet packages.
app.manifest Windows-only settings. Leave it as it is.

Rider shows each .axaml file with its .axaml.cs file nested underneath, because the two belong together.

The extension is .axaml, not .xaml, although the language is XAML. The different extension only exists so that IDEs never confuse Avalonia files with those of Microsoft’s XAML frameworks, which use .xaml.

1.3.1 How the application starts

Program.Main builds the application from the App class and starts it. App.axaml defines the application-wide resources, most importantly the theme:

<Application xmlns="https://github.com/avaloniaui"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             x:Class="HelloAvalonia.App"
             RequestedThemeVariant="Default">
    <Application.Styles>
        <FluentTheme />
    </Application.Styles>
</Application>

RequestedThemeVariant="Default" follows the operating system’s light or dark mode. Which window opens first is decided in code, in App.axaml.cs:

public override void OnFrameworkInitializationCompleted()
{
    if (ApplicationLifetime is IClassicDesktopStyleApplicationLifetime desktop)
    {
        desktop.MainWindow = new MainWindow();
    }

    base.OnFrameworkInitializationCompleted();
}

Program.cs also contains a call to .WithDeveloperTools(), surrounded by #if DEBUG. It connects debug builds to Avalonia’s developer tools; we don’t need them in this chapter, so leave the line as it is.

1.3.2 How XAML and code-behind are connected

Look at the top of MainWindow.axaml:

<Window ...
        x:Class="HelloAvalonia.MainWindow">

x:Class tells the XAML compiler that this markup belongs to the C# class HelloAvalonia.MainWindow (namespace plus class name). In MainWindow.axaml.cs that class is declared partial:

public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();
    }
}

At build time, Avalonia generates the second half of this partial class from the XAML file: a field for every named control, and the code that builds the controls. InitializeComponent(), called once in the constructor, runs that generated code. Without it the window would stay empty. Two files, one class.

The XAML is compiled straight into the program; it is not parsed at runtime. A typo in a property name is therefore a build error, not a crash when the window opens.

1.4 XAML basics

XAML uses XML syntax, so the usual XML rules apply:

  • A file has exactly one root element, and all other elements are correctly nested inside it. For a window, the root is <Window>; for a reusable part of a UI, it is a <UserControl>.
  • Element and attribute names are case-sensitive, and attribute values are always in double quotes.
  • The nesting of elements forms a tree. Avalonia turns that tree into the UI.

Every element stands for a class. When the window is created, <Button> creates a Button object through its parameterless constructor. Every attribute sets a public property of that object or subscribes to one of its events:

<Button Background="AliceBlue" Content="Click me!"/>

The attribute values are strings. Behind the scenes, type converters turn them into the right type, for example "AliceBlue" into a brush.

1.4.1 Namespaces

The root element of every XAML file declares at least two XML namespaces:

xmlns="https://github.com/avaloniaui"
xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
  • The first is the default namespace (no prefix). It contains all Avalonia controls, so you can write <Button> directly.
  • The second maps the XAML language namespace to the prefix x. Language features such as x:Class and x:Name come from there.

To use your own classes in XAML, declare a namespace for them with a prefix of your choice:

xmlns:models="using:HelloAvalonia.Models"

Then <models:Person/> creates a HelloAvalonia.Models.Person. For a class in a different assembly (another project or a NuGet package), the older form names the assembly as well: xmlns:logic="clr-namespace:LogicNamespace;assembly=Logic".

1.4.2 Property element syntax

Some values are too complex for a string. Instead of an attribute, you can then write the property as a child element named <Type.Property>:

<Button Background="AliceBlue">
    <Button.Content>
        <Ellipse Width="120" Height="90" Fill="LightBlue"/>
    </Button.Content>
</Button>

Here the button’s Content is no longer text but an Ellipse. Content is also the button’s content property, so you may leave out <Button.Content> and put the Ellipse directly between <Button> and </Button>.

1.4.3 Naming elements

To access an element from code, give it a name:

<TextBlock Name="CounterText" Text="Counter: 0"/>

The generated half of the partial class then contains a field CounterText of type TextBlock: the exact object the XAML created. x:Name="CounterText" does the same. Name is a property of the Avalonia controls, while x:Name is a XAML language feature that works on any element. For controls, use Name.

1.4.4 Markup extensions

Sometimes a property should not get a fixed value but one that comes from somewhere else. That is the job of markup extensions, written in curly braces. Here, the second button takes its background from the first:

<Button Name="Btn1" Background="LightYellow"/>
<Button Background="{Binding #Btn1.Background}"/>

#Btn1 refers to the element named Btn1. The most important markup extensions are:

Extension Description
Binding Takes the value from a data source and keeps it up to date (chapter Data Binding).
StaticResource Takes the value from a resource, once, when the element is created.
DynamicResource Takes the value from a resource and follows it when the resource changes.
TemplateBinding Used inside a control template (chapter Styles).

1.4.5 Styled properties

Avalonia controls don’t use plain C# properties for most of their settings. They use styled properties, which are registered with Avalonia’s property system (AvaloniaProperty.Register). You set and read them like any other property, but they can do more:

  • they have default values,
  • they notify Avalonia whenever their value changes,
  • they can validate new values and run a callback when the value changes.

That is what makes data binding, styles and animations possible: all three only work with styled properties. Every property of a built-in control that you would want to style or bind already is one.

1.4.6 Attached properties

An attached property is set on one element but belongs to another, usually the layout container around it. In this example, each button says at which edge of the DockPanel it wants to be docked:

<DockPanel>
    <Button DockPanel.Dock="Top">Click me!</Button>
    <Button DockPanel.Dock="Bottom">Click me too!</Button>
</DockPanel>

DockPanel.Dock only makes sense on a child of a DockPanel. Without attached properties, Button would need a Dock property, plus a property for every other container it could ever be placed in. The same mechanism places elements in the rows and columns of a grid, as you’ll see next.

1.5 A first layout

A Window can only have one direct child. To show more than one element, that child is a layout container (a panel), and everything else goes inside it. The two most common panels are:

  • Grid divides the space into rows and columns. RowDefinitions="*,Auto" creates two rows: the second is exactly as tall as its content (Auto), and the first takes all the remaining space (*). Children choose their row with the attached property Grid.Row.
  • StackPanel arranges its children one after another, vertically by default or horizontally with Orientation="Horizontal". Spacing adds a gap between the children.

The chapter Layouts and Controls covers all panels in detail.

TipLab 1.2: The layout

🎯 Goal. The window shows a greeting, a counter and four buttons. The buttons don’t do anything yet.

All changes are in MainWindow.axaml.

  1. In the <Window> start tag, change the title to Title="Hello Avalonia" and add after it:

    Width="480" Height="360" MinWidth="420" MinHeight="320"
WindowStartupLocation="CenterScreen"

    Also set d:DesignWidth="480" and d:DesignHeight="360". The d: attributes only apply to the previewer in the IDE; mc:Ignorable="d" tells the compiler to skip them.

  2. Replace the text Welcome to Avalonia! with a grid of two rows:

    <Grid RowDefinitions="*,Auto" Margin="32">
</Grid>

  3. Inside the grid, add the upper row, a StackPanel with the greeting:

    <StackPanel Grid.Row="0" Spacing="20"
            VerticalAlignment="Center" HorizontalAlignment="Center">
    <TextBlock Text="Hello, Avalonia!" FontSize="36" FontWeight="SemiBold"
               HorizontalAlignment="Center"/>
</StackPanel>

  4. In that StackPanel, below the greeting, add a button and the counter:

    <Button Content="Click me!" Classes="accent" Padding="24,10"
        HorizontalAlignment="Center"/>
<TextBlock Text="Counter: 0" FontSize="16" Opacity="0.7"
           HorizontalAlignment="Center"/>

    Classes="accent" paints the button in the system’s accent color (chapter Styles).

  5. Below that StackPanel, still inside the grid, add the lower row:

    <StackPanel Grid.Row="1" Orientation="Horizontal" Spacing="12"
            HorizontalAlignment="Center">
    <Button Content="Increment counter" Padding="16,8"/>
</StackPanel>

    Then add two more buttons to it yourself: Popup message and Close, with the same padding.

✅ Check. dotnet run: the window is centered on the screen, the greeting and counter sit in the middle, and the three buttons are lined up along the bottom. Make the window narrower and wider: the layout adapts, but the window can’t get smaller than 420 × 320.

1.6 Events

To react to user input, you attach a handler method to an event. The method runs every time the event occurs. There are two ways to attach it.

In XAML, name the method in the event attribute. The method must exist in the code-behind:

<Button Name="DemoButton" Content="Click me!" Click="OnDemoButtonClicked"/>
private void OnDemoButtonClicked(object? sender, RoutedEventArgs e)
{
    DemoButton.Content = "Clicked!";
}

In code, subscribe to the event in the constructor, after InitializeComponent() has created the controls:

public MainWindow()
{
    InitializeComponent();
    DemoButton.Click += OnDemoButtonClicked;
}

Both do the same. The labs use the XAML form. Later, with MVVM, most event handlers are replaced by commands.

A few conventions that the handlers in this book follow:

  • Handlers are private: only the window itself needs them.
  • The signature is (object? sender, RoutedEventArgs e). sender is the control that raised the event.
  • Names follow the pattern On<Control><Event>, e.g. OnCloseButtonClicked, so you can quickly find the handler of a XAML attribute.

1.6.1 Routed events

Click is a routed event: it doesn’t stay at the button you clicked. It first fires on the button, then on the button’s parent, then on its parent, all the way up to the window. This is called bubbling. Because of it, one handler on a container can react to clicks on any button inside it.

When two nested controls both handle the same event, the inner handler can stop it with e.Handled = true, and the outer control never sees it.

1.6.2 State lives in the code-behind

As long as there is no data binding, the state of the window is just a field in the MainWindow class. A handler changes the field and then updates the UI by hand:

private int _counter;

private void OnIncrementCounterButtonClicked(object? sender, RoutedEventArgs e)
{
    _counter++;
    CounterText.Text = "Counter: " + _counter;
}

Forgetting the second line is a classic bug: the state changes, the screen doesn’t. Data binding (chapter Data Binding) removes exactly this manual step.

TipLab 1.3: The counter

🎯 Goal. Increment counter counts up, and Close closes the window.

  1. In MainWindow.axaml, add Name="CounterText" to the counter’s TextBlock, and Click="OnIncrementCounterButtonClicked" to the Increment counter button.

  2. In MainWindow.axaml.cs, add using Avalonia.Interactivity; at the top (for RoutedEventArgs). Then add the field _counter and the method OnIncrementCounterButtonClicked from the section State lives in the code-behind to the class.

  3. Now the Close button, on your own: add Click="OnCloseButtonClicked" to it and write the handler. A window closes itself with Close().

✅ Check. Each click on Increment counter raises the number by one. Close ends the app.

💡 Try it. Rename OnCloseButtonClicked in the C# file only and build. The XAML compiler checks that every handler named in XAML exists, but its message is not very clear: AVLN3000: Unable to find suitable setter or adder for property Click. It does point at the right line and column of MainWindow.axaml, though. Remember this message: it almost always means a misspelled handler name. Undo the rename afterwards.

1.7 Dialogs

Avalonia itself has no ready-made message box. The NuGet package MessageBox.Avalonia provides one. It can show a dialog in two ways:

  • ShowAsync() opens it as a separate window.
  • ShowAsPopupAsync(this) shows it as an overlay inside this window.

Both methods return a Task, so they are awaited, and the handlers that call them are marked async. A handler is then async void, which is normally a mistake in C#: nobody can await the method, and an exception thrown in it can’t be caught by the caller. Event handlers are the one accepted exception, because events require methods that return void. Every other async method, including those called from an event handler, returns a Task.

TipLab 1.4: Dialogs

🎯 Goal. Click me! asks whether to quit, and Popup message shows a message inside the window.

  1. Add the package:

    dotnet add package MessageBox.Avalonia --version 12.0.0

  2. In MainWindow.axaml, add Click="OnGreetButtonClicked" to the Click me! button.

  3. In MainWindow.axaml.cs, add two lines at the top:

    using MsBox.Avalonia;
using MsBox.Avalonia.Enums;

    and this handler to the class:

    private async void OnGreetButtonClicked(object? sender, RoutedEventArgs e)
{
    var box = MessageBoxManager.GetMessageBoxStandard(
        "Hello", "Hello from Avalonia! Do you want to quit?", ButtonEnum.YesNo);
    var result = await box.ShowAsync();
    if (result == ButtonResult.Yes)
    {
        Close();
    }
}

  4. Now Popup message, on your own: attach a handler OnShowPopupButtonClicked and show a message box with only a title and a text (no ButtonEnum). Show it with ShowAsPopupAsync(this) instead of ShowAsync().

✅ Check. Click me! opens a separate dialog window; Yes closes the app, No only the dialog. Popup message shows the message as an overlay inside the main window, not as a window of its own.

1.8 Window events

Besides the events of its controls, a window has events of its own. The most useful ones:

Event Occurs when
Opened the window has been shown for the first time.
Loaded the window and all its controls are created and laid out. Initialization code that needs the controls belongs here.
Activated / Deactivated the window becomes the active window, or another window does.
PositionChanged the window was moved.
SizeChanged the window’s size changed.
Closing the window is about to close. Setting e.Cancel = true in the handler keeps it open, e.g. to ask about unsaved changes.
Closed the window has been closed.

There is no event for minimizing or maximizing. The WindowState property holds that state; subscribe to PropertyChanged and check whether e.Property is Window.WindowStateProperty to be notified.

1.9 The previewer

Rider (with the AvaloniaRider plugin) and VS Code (with the Avalonia extension) render a live preview of an .axaml file next to the editor, without starting the app. That’s handy for adjusting a layout. The d: attributes from Lab 1.2 set the size of that preview.

The previewer is not completely reliable. It can lag behind your edits, keep showing an error you already fixed, or fail to load for reasons that have nothing to do with your XAML. A rebuild usually clears it. A red previewer is no proof that your XAML is wrong: check with dotnet build first.

1.10 Try it yourself

Extend HelloAvalonia:

  1. Add a button that resets the counter to 0.
  2. Disable Increment counter once the counter reaches 10. Every control has an IsEnabled property.
  3. Swap ShowAsync and ShowAsPopupAsync in the two dialog handlers and compare.
  4. Add a TextBox and change the greeting dialog to greet the name entered there. A TextBox has a Text property.
  5. Handle the window’s Closing event: ask “Do you really want to quit?” and keep the window open when the answer is No. Watch out: the handler can’t wait for the dialog before deciding, because the window closes as soon as the handler returns. Cancel first, ask, and call Close() yourself on Yes. Then make sure that this second Close() doesn’t ask again.
