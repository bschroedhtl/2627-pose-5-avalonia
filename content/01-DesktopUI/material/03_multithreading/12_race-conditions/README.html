12  Race Conditions

Running work in parallel is the easy part. As soon as two threads touch the same data, results can go wrong in ways that are hard to see and harder to reproduce. This chapter shows how, and the next one how to prevent it.

12.1 What a race condition is

A race condition is a bug where the result depends on the relative timing of two or more threads. The same code, run twice on the same input, can produce different answers.

A race needs shared mutable state: two or more threads reaching the same variable, and at least one of them writing. Remove any one of those three — sharing, mutation, or concurrency — and the race is gone.

12.2 Anatomy: the lost update

This innocent line is the classic example:

counter += batch;

It looks like one operation. At machine level it is three:

  1. read the current value of counter
  2. add batch to it
  3. write the result back

Nothing prevents another thread from doing its own read between your read and your write:

thread A thread B counter
read → 5000 5000
read → 5000 5000
add 400 → 5400 5000
add 300 → 5300 5000
write 5400 5400
write 5300 5300 ← A’s 400 is lost

Both threads did their job, and one update vanished. This is a lost update.

It is not theoretical. Eight threads reporting their progress into one shared counter, 2,000,000 increments in total, ten consecutive runs of the identical program:

run counted lost
1 1,889,250 110,750
2 1,987,500 12,500
3 1,976,450 23,550
10 1,997,850 2,150

Wrong in 10 out of 10 runs, and never by the same amount. A result that changes between runs of identical code is the signature of a race condition.

Run it yourself: the console program CounterThreadSynchronization, handed out with the π-calculator exercise, does exactly this, and then repeats it with each of the fixes described in the chapter Protecting Critical Sections — so you can watch the losses appear, disappear, and compare what each mechanism costs.

12.3 Why these bugs are dangerous

Notice what did not happen: nothing crashed, and no exception was thrown. In those same runs the threads’ actual computed results were all correct, because each thread kept its own partial result in its own storage and shared nothing. Only the shared counter was wrong.

Concurrency bugs routinely look exactly like this — a plausible answer, no error, slightly wrong. You cannot wait for a crash to find them. You have to reason about which state is shared.

12.4 Other kinds of races

Check-then-act. The check and the action are separately correct but not atomic:

if (!dictionary.ContainsKey(key))   // thread B can insert right here
    dictionary.Add(key, value);     // -> exception, or a lost value

Torn reads. A read that catches a value mid-write. On a 32-bit runtime a long is written in two 32-bit halves, so a reader can observe half of the old value and half of the new — a number that was never assigned.

Stale reads and reordering. Compiler and CPU may cache a value in a register or reorder instructions. A thread can keep seeing an old value long after another thread changed it. This is what volatile addresses — and only this.
