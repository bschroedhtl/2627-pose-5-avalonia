13  Protecting Critical Sections

A critical section is a region of code that must not be executed by more than one thread at a time. The options below go from cheapest and most preferable to most specialised; the table at the end helps to choose.

13.1 Don’t share (always try this first)

The best fix is to remove the sharing. Give each worker its own storage and combine at the end:

var results = new double[workers];
// each thread writes only results[myIndex] - distinct memory, no synchronization needed
...
var average = results.Average();    // combine on one thread, after all Joins

Different array elements are independent locations, so this is safe with no locking at all. Immutable data is likewise safe by construction. Most concurrency bugs are best fixed by not sharing, not by locking harder.

13.2 Interlocked: atomic operations on a single variable

Interlocked.Add(ref _counter, batch);
Interlocked.Increment(ref _counter);
var old = Interlocked.Exchange(ref _flag, 1);
Interlocked.CompareExchange(ref _value, newValue, expected);

These perform read-modify-write as one indivisible CPU instruction. No thread can interleave, and no thread ever waits — this is lock-free, and the cheapest correct option.

The catch: it needs a ref to a field, and you cannot pass a property with ref. That is why a counter exposed as a property needs an explicit backing field:

private long _processed;                    // the field Interlocked works on
public long Processed => _processed;        // read-only view for the outside world

public void Report(long batch) => Interlocked.Add(ref _processed, batch);

Use it when you are guarding one variable. It cannot make two updates atomic together.

13.3 lock: mutual exclusion

private readonly object _sync = new();

lock (_sync)
{
    _total += batch;        // several statements can be made atomic
    _count++;               // as one unit
}

lock is syntactic sugar for Monitor.Enter/Exit in a try/finally. Use it when an invariant spans more than one variable — exactly what Interlocked cannot do.

Rules:

  • Lock on a private readonly object. Never lock(this) (outside code can lock your instance), never a string (interned — shared process-wide), never a Type.
  • Keep it short. Every other thread that arrives has to wait; a long critical section serialises your program and undoes your parallelism.
  • No await inside a lock — it will not compile, and for good reason: a lock is owned by a thread, and the continuation after an await may run on a different one.
  • Always take multiple locks in the same order everywhere. Two threads taking A→B and B→A is a deadlock: each holds what the other needs, and neither ever proceeds.

In .NET 9+, prefer the dedicated System.Threading.Lock type over a plain object — it is faster and lock (myLock) gets compile-time checking. A plain object still works everywhere.

13.4 Concurrent collections

var queue = new ConcurrentQueue<Dot>();      // producers Enqueue, consumer TryDequeue
var map = new ConcurrentDictionary<K, V>();

Each individual operation is thread-safe, so you do not need your own lock around them. But compound operations still are not atomic — if (!map.ContainsKey(k)) map.TryAdd(k, v) has the same check-then-act bug as in the chapter Race Conditions. Use the purpose-built atomic methods instead: GetOrAdd, AddOrUpdate, TryUpdate.

13.5 SemaphoreSlim: when you need to await inside

private readonly SemaphoreSlim _gate = new(1, 1);

await _gate.WaitAsync();
try { await SomethingAsync(); }
finally { _gate.Release(); }

The async-friendly alternative to lock, and the tool for limiting concurrency to n rather than 1. Always Release in a finally.

13.6 ReaderWriterLockSlim: many readers, rare writers

Lets any number of readers in simultaneously but excludes them while a writer works. Worth it only when reads dominate heavily and the critical section is genuinely expensive; otherwise lock is simpler and often faster.

13.7 What volatile does — and does not — do

volatile is the most commonly misapplied keyword in this area.

private volatile bool _stopRequested;   // GOOD: a flag one thread sets, another polls
private volatile long _counter;         // USELESS: counter += x is still not atomic

volatile guarantees visibility and ordering — you read a fresh value rather than a cached one, and the compiler will not reorder around it. It says nothing about atomicity. All three steps of += can still interleave, and updates are still lost. (It also cannot be applied to long or double, so the second line does not even compile.) For a counter you need Interlocked; for a stop flag volatile is exactly right.

13.8 Choosing

Situation Use
Each worker can have its own copy no synchronization — combine at the end
One counter or flag, simple update Interlocked
A flag one thread sets, another reads volatile (or Volatile.Read/Write)
Invariant across several fields lock
Shared collection ConcurrentQueue / ConcurrentDictionary
Need to await in the critical section SemaphoreSlim
Reads vastly outnumber writes ReaderWriterLockSlim
