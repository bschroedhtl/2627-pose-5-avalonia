10  CPU-bound vs. I/O-bound

A desktop application may use every core of the machine, and a calculation that runs for seconds is worth spreading across all of them. This part is the theory for that: it has no labs, and the π-calculator exercise puts it into practice. Its chapters follow three questions, in the order you should ask them:

  1. What is my code waiting for? CPU-bound vs. I/O-bound (this chapter)
  2. How do I run it in parallel? Threads and Tasks
  3. What breaks when I do? Race Conditions, and Protecting Critical Sections

The last chapter, The UI Thread, shows the extra rule a UI application adds.

10.1 What is my code waiting for?

Before reaching for a thread, work out what the code is actually waiting for. This single question decides which tool is correct — and picking the wrong one usually makes things worse, not just no better.

CPU-bound I/O-bound
The code is waiting for a processor core a device (disk, network, database)
While waiting, the CPU is busy at 100% idle
Typical examples Monte Carlo simulation, image filters, encryption, sorting a huge list, parsing HTTP requests, file reads, SQL queries, waiting for user input
Gets faster with more threads yes, up to your core count no
The right tool Task.Run / threads / SIMD async/await
What you gain throughput — the work finishes sooner scalability — you can serve far more work at once

The single most important thing to understand before any of the rest: async/await does not create threads. It is a mechanism for giving a thread back while you wait for something that isn’t the CPU. The sections below show what that means in each of the two cases.

10.2 The Task Parallel Library

TPL stands for Task Parallel Library — the System.Threading.Tasks namespace, added in .NET 4 and the standard way to do concurrency in .NET ever since. async/await, Task.Run, Task.WhenAll, Parallel.For and PLINQ are all part of it.

The shift it introduced is one of vocabulary, and it is worth stating plainly:

With threads you describe workers — “create a worker, start it, wait for it to finish.” With the TPL you describe work — “here is a job; run it and give me the result.” Which thread runs that job, and when, becomes the library’s problem rather than yours.

The TPL runs work on the thread pool: a set of reusable worker threads that it hands work items to. The chapter Threads and Tasks compares the two models in detail.

10.3 I/O-bound work: waiting without a thread

So what actually happens when you await an I/O call? Follow one line through, step by step:

var text = await File.ReadAllTextAsync(path);
Console.WriteLine(text.Length);          // the "continuation"
  1. Your method asks the operating system to start the read and returns immediately — it does not wait. The caller gets back an unfinished Task.
  2. The thread that was running your method is now free. It goes back to the thread pool and does something else.
  3. The disk works. No thread is involved at all during this time — the operation is in the hands of the hardware and the OS.
  4. When the data is there, the OS notifies .NET, which schedules the rest of your method — the code after the await — as a new work item.
  5. A thread picks that work item up and runs Console.WriteLine(text.Length). It may well be a different thread than the one from step 1.

Drawn on a time axis, with a four-thread pool underneath:

time ------------------------------------------------------------------------------>

steps 1-2                    step 3                       steps 4-5
+-----------------------+    +-----------------------+    +-----------------------+
|    THREAD OCCUPIED    | -> |    NO THREAD HELD     | -> |    THREAD OCCUPIED    |
+-----------------------+    +-----------------------+    +-----------------------+
thread A runs your method    A is back in the pool,       a thread is taken from
and starts the read          free for other work          the pool to run the rest
                             (the disk is working)        of your method

the thread pool meanwhile:
+-----+-----+-----+-----+    +-----+-----+-----+-----+    +-----+-----+-----+-----+
|  A  |  B  |  C  |  D  |    |  A  |  B  |  C  |  D  |    |  A  |  B  |  C  |  D  |
| ### |  .  |  .  |  .  |    |  .  |  .  |  .  |  .  |    |  .  | ### |  .  |  .  |
+-----+-----+-----+-----+    +-----+-----+-----+-----+    +-----+-----+-----+-----+
A occupied by your code      no thread is occupied        B - a DIFFERENT thread -
                             on your behalf               runs the continuation

The middle phase is not drawn to scale: reading a file takes milliseconds and a network call tens of milliseconds, while the two occupied phases are a few microseconds each. In other words, the overwhelming majority of the elapsed time is spent in the middle box, where your code holds no thread at all. Had you used the blocking File.ReadAllText instead, thread A would have stayed occupied — and useless — across all three boxes.

The key point: a thread is held only while your code is actually executing, never while it is waiting for a device. That is what lets a web server handle tens of thousands of simultaneous requests on a handful of threads — nearly all of them are waiting, and waiting is free.

10.4 CPU-bound work: moving it off the caller

Now the other case. This looks almost identical at the call site:

var result = await Task.Run(() => Calculate(1_000_000_000));

but the middle box of the diagram above simply does not exist. There is no device to wait for — a core has to execute those billion iterations — so a thread stays occupied for the entire duration. Nothing is given back.

That means Task.Run here does not make the calculation faster. What it does is move the work off the calling thread. That matters enormously when the caller is the UI thread: without it the window freezes for the whole calculation, because the thread that should be redrawing the window is busy doing arithmetic instead. The await keeps the UI responsive; it does not shorten the computation by a single millisecond.

The actual speed-up has to come from somewhere else — splitting the work across several cores, which is what the next chapters are about.

I/O-bound await CPU-bound Task.Run
Thread held while working no yes, the whole time
What await buys you scalability — thousands of waits, few threads responsiveness — the caller stays free
How it gets faster it doesn’t need to; waiting is free more cores, or SIMD

10.5 Two mistakes worth naming

Fake async — wrapping blocking I/O in Task.Run:

// BAD: burns a pool thread that just sits there waiting for the disk
var text = await Task.Run(() => File.ReadAllText(path));

// GOOD: no thread is held while the disk works
var text = await File.ReadAllTextAsync(path);

The first version is not more scalable than the blocking call — it is less, because you now block a pool thread instead of your own, and the pool has better things to do. On a server this is a classic cause of thread-pool starvation.

Blocking on async code — .Result or .Wait():

var data = FetchAsync().Result;   // BAD: blocks, and can deadlock outright

This throws away the entire benefit and, in a context with a synchronization context (older UI frameworks, ASP.NET), can deadlock: the continuation needs the thread you are blocking. Rule of thumb: async all the way up.

10.6 Summary

async/await makes code wait without blocking. Threads make code run in parallel. Only CPU-bound work benefits from more threads, and only I/O-bound work benefits from async.

A simulation that does nothing but arithmetic — no disk, no network — is a textbook CPU-bound problem. That is precisely why multithreading pays off for it, and why async alone would achieve nothing.
